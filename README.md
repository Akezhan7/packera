# Vue 3 + Vite

Главный экран управляется в разделе «Баннеры» существующей админки: главный блок редактируется отдельно от рекламной ленты. Для акций доступны информационное окно, категория, задача, товар, ссылка http/https или внутренний путь, а также отсутствие действия. Даты публикации задаются в UTC+5 при включении расписания. Заголовки, описания и кнопки заполняются на RU/KK. По умолчанию загружается одно изображение для всех устройств; отдельное мобильное фото находится в необязательных настройках. Смена основного изображения убирает прежнее мобильное фото. Изображения заполняют область баннера с кадрированием, без внутренних полей.

Для загруженных JPEG/PNG витрина запрашивает WebP-копии через `/products/upload_…?w=320|640|960|1280&format=webp`; стандартный `Artboard 1.png` использует `/products/hero-banner` с теми же параметрами. Sharp создаёт копии при первом запросе (не более двух обработок одновременно) и сохраняет их в `public/products/.thumbnails`; оригиналы и фотографии полноэкранной галереи не меняются. Прозрачность PNG сохраняется, прежние ссылки без `format` продолжают работать. При заполнении очереди отдаётся оригинал без кеширования ответа, чтобы доступная фотография продолжала отображаться. Кеш стандартного hero учитывает изменение исходного файла и имеет срок один день; уникальные загруженные изображения и их копии кешируются на год. Каталог API и серверный HTML остаются без кеширования. Библиотеки админки загружаются отдельно от витрины.

Inter и Outfit размещены локально в `public/fonts`, с прежними весами и языковыми диапазонами. Font-face подключается в основной CSS с `font-display:swap`; блокирующего внешнего CSS Google Fonts нет. Файлы лицензий OFL находятся рядом со шрифтами.

SEO-роадмап: [docs/seo-roadmap.md](docs/seo-roadmap.md). Основной домен — `https://packera.kz/`. Главная и `/admin` остаются рабочими; `/admin/` и `/index.html` перенаправляются на канонические пути. Неизвестные адреса и отсутствующие файлы возвращают 404. Админка и API получают `X-Robots-Tag: noindex`; robots.txt разрешает `/api/data` для чтения текущей SPA и не закрывает админку от обхода, чтобы робот мог увидеть noindex. Robots содержит ссылку на динамический `/sitemap.xml`. Альтернативные домены перенаправляются только при попадании запроса на этот сервер; DNS, TLS и правила Cloudflare проверяются отдельно владельцем.

Публичные страницы: `/product/id-<ID товара>`, `/catalog/id-<UUID категории>`, `/tasks/id-<ID задачи>`; ID кодируется как сегмент URL, переименование адрес не меняет. Удалённый объект или скрытый товар возвращает 404. Сервер читает актуальный снимок из БД и возвращает индивидуальные title, description, canonical и Open Graph без кеширования HTML. Ссылки названий товаров, категорий, задач и действия баннеров открывают эти страницы. Страница товара использует контролы каталога; выбранный размер передаётся в `?size=…`, его смена заменяет текущую запись истории, canonical остаётся без параметров. Неизвестный размер убирается из URL временным перенаправлением 307, используется исходная обложка и обычный первый размер для цены и корзины. Ошибка загрузки реальных данных на отдельной странице показывает сообщение и повторную загрузку. Браузерные переходы сохраняют корзину; перезагрузка сохраняет прежнее поведение корзины.

Главная, товары, категории и задачи рендерятся текущими Vue-компонентами на сервере: текст, характеристики, цена выбранного размера и ссылки доступны без JavaScript. API и SSR читают одинаковый согласованный снимок PostgreSQL через `server/catalog.js`; скрытые товары исключаются из HTML и встроенного снимка. На каждый SSR-запрос создаётся независимое состояние. Клиент гидратирует тот же HTML и снимок без повторного начального запроса API. Язык главной и задачи задаётся URL; на непереведённых страницах каталога сохранённый язык интерфейса восстанавливается после гидратации. Закрытые модальные окна подключаются после монтирования. HTML и API не кешируются, следующий запрос после сохранения получает актуальные данные. Подход соответствует [документации Vue SSR](https://vuejs.org/guide/scaling-up/ssr.html).

`npm run build` создаёт клиентский `dist` и серверный `dist-ssr`; для публичных страниц нужны обе сборки, затем перезапуск Node. Dockerfile включает обе автоматически. `/admin` сохраняет клиентский запуск и существующее API. `dist-ssr` не публикуется как статический каталог. `npm run preview` предназначен для клиентской сборки; для проверки SSR запускайте `npm run server`. Vite dev сохраняет прежнюю работу через API. Проверки SSR/SEO: после `npm run build` выполнить `node --test tests/server-rendering.test.js tests/server-rendering-api.test.js tests/seo.test.js tests/public-routes.test.js tests/product-images.test.js tests/structured-data.test.js`. Интеграционная проверка создаёт собственную временную БД и не меняет сохранённую локальную витрину.

Русские канонические адреса сохраняются. `/kk/` доступен при заполненных переводах главного блока; `/kk/tasks/id-<ID>` — при заполненных `titleKk` и переводе непустого описания задачи. Для таких пар сервер и клиент выставляют `lang`, взаимные `hreflang` RU/KK и `x-default`, отдельный canonical и Open Graph locale; языковые переключатели работают как ссылки. Товары и категории пока не имеют переводов в БД: их KK-адреса возвращают 404, ссылки ведут на RU-страницы. Названия товаров внутри KK-витрины сохраняют исходный язык. Удаление перевода исключает соответствующий адрес и альтернативу. Используется [рекомендованный Google подход к языковым версиям](https://developers.google.com/search/docs/specialty/international/localized-versions).

Публичный HTML содержит JSON-LD `Organization`, `BreadcrumbList` и на странице товара — `Product`/`Offer`: описание, характеристики, фактические фотографии и цена выбранного размера (по умолчанию первого, как в интерфейсе), валюта KZT и ссылка на этот вариант. Разметка обновляется при переходах и выборе размера, удаляется в админке и на недоступных страницах. Контакты, описание доставки, порог бесплатной доставки и правило галереи разделяются с интерфейсом через `shared`. Подтверждённые данные: Алматы, ул. Ратушного, 78в; +7 707 944 00 55; вторник–воскресенье; рассрочка Kaspi/Halyk/Forte; доставка по Казахстану, по Алматы бесплатно от 70 000 ₸ включительно. Эти сведения отображаются на RU/KK; адрес и территория обслуживания также присутствуют в Organization. Часы открытия/закрытия, сроки и прочая стоимость доставки, условия возврата не указаны; соответствующие свойства не добавляются. Товары и категории остаются на RU по решению владельца, миграция переводов не нужна. Наличие, SKU, рейтинги и производитель не выдумываются. Основа разметки — [Product](https://developers.google.com/search/docs/appearance/structured-data/product-snippet) и [Organization](https://developers.google.com/search/docs/appearance/structured-data/organization).

Миграция `004-marketing` автоматически применяется при запуске сервера, добавляет поля баннеров и фотографии задач, а также настройку `hero`; существующие данные сохраняются. В разделе «Задачи» фото карточки для ПК и картинка мобильной кнопки загружаются независимо. Мобильные кнопки компактные, в две колонки: готовая картинка содержит название и визуал (рекомендуемый формат 640 × 200 px), дополнительный текст не накладывается. Без мобильной картинки используются текущее название RU/KK и иконка. Общие названия сохраняются для ПК, рекомендаций и доступности; текст внутри картинки автоматически не переводится. Галерея товара начинает с обложки и общих фото; после выбора размера показывает его фотографии и общие слайды, а при отсутствии фото размера — обложку и общие слайды.

`/sitemap.xml` строится при запросе из согласованного снимка каталога и возвращает `application/xml; charset=utf-8`, `Cache-Control: no-store`. Включает главную, видимые товары, категории, задачи и доступные KK-версии с взаимными XHTML-alternate ссылками. Админка, API, скрытые/удалённые товары и параметры вариантов исключены. Имена можно менять без смены адресов; скрытие, удаление и изменение перевода учитываются в следующем запросе. `lastmod` не придумывается: страницы подборок меняются также при изменении связанных товаров. Для текущего каталога достаточно одной карты; превышение лимитов протокола возвращает ошибку, вместо обрезанной/некорректной карты. Подход соответствует [правилам sitemap Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap). Точечная проверка: `node --test tests/sitemap.test.js tests/seo.test.js tests/server-rendering-api.test.js` после сборки.

После публикации проверить реальные типы ответов `/robots.txt` и `/sitemap.xml`, подтвердить владение `packera.kz` в [Search Console](https://support.google.com/webmasters/answer/9008080), отправить `https://packera.kz/sitemap.xml` и проверить URL главной, товара, категории и RU/KK-задачи. [Bing позволяет импортировать подтверждённый сайт из Search Console](https://www2.bing.com/webmasters/help/add-and-verify-site-12184f8b). Снять базовые показатели показов/кликов и индексирования; их сейчас нельзя получить без доступа к кабинетам.

Проверять блокировки в Cloudflare по реальным запросам и проверенным IP, не разрешать ботов только по User-Agent: [Google проверяет источник по IP или обратному/прямому DNS](https://developers.google.com/crawling/docs/crawlers-fetchers/verify-google-requests), [Bing предоставляет Verify Bingbot](https://www.bing.com/webmasters/help/verify-bingbot-2195837f), [Cloudflare описывает Verified bots](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/). [OAI-SearchBot используется для поиска, GPTBot — для обучения; настройки независимы](https://developers.openai.com/api/docs/bots). Приложение сохраняет существующий wildcard-доступ, отдельная политика GPTBot не вводилась; для OAI-SearchBot сверять актуальные опубликованные OpenAI диапазоны IP. Не менять защиту админки/API ради обхода публичных страниц. Публичный запрос с подставленным User-Agent не доказывает доступ настоящего робота; для завершения внешней части нужны кабинеты владельца.

## Локальная авторизация админки

Админка использует аккаунты PostgreSQL. Прежние общие пароли `admin`/`admin123` и флаг sessionStorage больше не предоставляют доступ. При старте backend применяет версионируемые миграции `server/migrations`; существующие товары не удаляются.

Перед запуском явно задайте `DATABASE_URL` своей локальной PostgreSQL. Backend: `npm run server`; frontend и backend: `npm run dev`. Порт backend по умолчанию 3002. Для проверки готовой сборки выполните `npm run build`, затем `npm run server` и откройте `/admin` на этом порту.

Первого главного администратора создаёт `node scripts/create-admin.js` в интерактивном терминале с явно заданным `DATABASE_URL`. Скрипт запрашивает логин, имя и пароль, скрывает ввод пароля и требует повторного ввода. Пароль — 12–128 символов; логин — 3–64 латинских буквы, цифры, точка, дефис или подчёркивание. Если действующий главный администратор уже есть, повторное создание через bootstrap запрещено.

Сессия действует 12 часов и передаётся HttpOnly-cookie. Для production нужен HTTPS: при `NODE_ENV=production` cookie имеет Secure. `CORS_ORIGIN` принимает список доверенных origin через запятую для отдельно размещённого frontend; текущий origin самого backend разрешён проверкой CSRF. Пароли, session-cookie и DATABASE_URL с реальными секретами не хранить в репозитории. `api/index.js` использует тот же backend PostgreSQL; режим Vercel KV отключён и при соответствующих KV-переменных запуск завершается явной ошибкой.

Роль `admin` имеет доступ к журналу изменений; роль `editor` — к обычному редактированию. Сброс полного содержимого отключён для всех ролей. Управление пользователями доступно администраторам. При истечении сессии форма товара/задачи сохраняет черновик до повторного входа в той же открытой странице; перезагрузка страницы черновик не сохраняет.

## API сохранения (этап 3)

Запись полного снимка `/api/save` и сброс `/api/reset` отключены: HTTP 410 без изменения данных. Админка использует адресный batch и не вызывает старое сохранение.

Рабочие API требуют сессию и `X-CSRF-Token`:

- POST `/api/products`, `/api/categories`, `/api/tasks`, `/api/banners`: поля нового объекта; `id` обязателен у товара/задачи, у категории/баннера может быть создан сервером. Ответ 201: `{success, data, changes}`.
- PATCH `/api/<entity>/:id`: `{version, changes: {поле: значение}}`; `version` — версия объекта при открытии формы. ID категории — стабильный UUID, название можно изменять.
- DELETE `/api/<entity>/:id`: `{version}`. Наличие или отсутствие объекта в загруженном каталоге само по себе не удаляет его.
- PATCH `/api/settings`: `{key: "installmentEnabled", version, changes: {value: false}}`. Публичный GET `/api/data` сохраняет `siteSettings` с прежними boolean-значениями и добавляет `settingVersions`.
- POST `/api/content/batch`: `{operations: [...]}`. Создание: `{entity, action: "create", data}`; изменение: `{entity, action: "update", id, version, changes}`; удаление: `{entity, action: "delete", id, version}`. Допустимые entity: products, categories, tasks, banners, settings. До 2000 операций, без повторения одного объекта; полный rollback при любой ошибке. Settings допускает только update. Ответ `{success, results, changes}`.
- GET `/api/audit`: только admin; фильтры entity/id/actor/from/to, limit 1–100 (по умолчанию 50), offset. Даты ISO; ответ `{items, total, limit, offset}`.

`changes` содержит все затронутые объекты `{entity, id, data}`; `data: null` означает удаление. Переименование/удаление категории и удаление задачи автоматически меняют соответствующие связи товаров и их версии в той же транзакции. Клиент должен применять весь список подтверждённых изменений.

409 VERSION_CONFLICT возвращает `{error, code, entity, id, current}`. 404 NOT_FOUND означает, что объект удалён. 409 ALREADY_EXISTS запрещает дублировать ID/имя. Версия — непрозрачный возрастающий integer из общей последовательности; клиент сохраняет возвращённое значение и не вычисляет следующую версию. Повторное создание того же ID получает другую версию. Последовательность не откатывается вместе с транзакцией, поэтому пропуски версий нормальны.

Журнал и данные записываются одной транзакцией. Для небольшого потока запросов админки записи используют один transaction advisory lock; это также защищает связи категорий/задач и исключает взаимные блокировки внутри batch. Публичный каталог читается из согласованного snapshot PostgreSQL. Все записи текущего приложения проходят через этот API; старые SQLite/restore-скрипты в корне не входят в npm/Docker-запуск и не предназначены для online-редактирования рабочей БД.

Удалённые задачи не восстанавливаются при перезапуске. Стандартные задачи создаются только при первоначальном создании таблицы.

## Сохранение в админке (этап 4)

Товар и задача сохраняются только кнопкой «Сохранить изменения». Крестик/отмена ничего не записывают и предупреждают о несохранённых правках. Категории, баннеры, настройки и сортировка сохраняются отдельными явными действиями; общий каталог обновляется после ответа сервера. При конфликте свежая версия и черновик отображаются рядом: загрузите свежую версию и вручную перенесите нужные изменения. Автоматического принудительного сохранения нет. При 404 объект удалён и старое сохранение не восстановит его.

Если ответ потерян, приложение проверяет актуальное состояние без HTTP-cache. При недоступном сервере новые записи блокируются до «Проверить результат»; не перезагружайте страницу с черновиком. При отзыве сессии войдите заново в той же странице. Fallback-каталог витрины не допускается к админской записи. Дождитесь окончания загрузки фотографий перед сохранением.

Импорт XLSX/XLS/CSV: первая вкладка, обязательные столбцы `ID`, `Название`, `Цена` (также принимаются `ID`, `Title`, `Price`). Дополнительные: `Описание`/`Description`, `Категория`/`Category`, `Единица`/`Unit`, `Фото`/`Image`, `Фотографии`/`Images` (URL через `;`), `Размеры`/`Sizes` и `Характеристики`/`Specs` (JSON), `KaspiLink`, `HalykLink`, `ForteLink`, `task:<ID задачи>` (0–3). Просмотрите список, затем нажмите «Сохранить импорт». Незаданные столбцы существующего товара сохраняются; товары не удаляются. Новые категории создаются в той же транзакции. Максимум 2000 операций; ошибка любой строки откатывает всё. При конфликте проверьте свежий каталог и подготовьте исправленный файл заново: автоматической смены версий импорта нет.

SheetJS 0.20.3 устанавливается из [официального CDN](https://docs.sheetjs.com/docs/getting-started/installation/nodejs/); источник и контрольная сумма закреплены в package-lock.json. В CSV отключено автоматическое преобразование значений, чтобы ID `001` не становился `1`; цены проверяются существующей логикой подготовки импорта. Проверка чтения XLSX/XLS/CSV: `node --test tests/admin-import.test.js`.

## Пользователи и история (этап 5)

Администратору доступны разделы «Пользователи» и «История изменений». Редактор работает с каталогом; управление доступом и чтение журнала ему запрещены также сервером.

API: GET/POST /api/users; PATCH /api/users/:id; POST /api/users/:id/reset-password. Создание принимает login, name, role (admin/editor), temporaryPassword. PATCH принимает updatedAt из списка и changes с изменёнными login/name/role/isActive. Сброс принимает updatedAt и temporaryPassword. Конфликт устаревшей формы возвращает 409 USER_CONFLICT и актуальные публичные данные; логин занят — 409 LOGIN_TAKEN; отключение/понижение последнего активного администратора — 409 LAST_ADMIN. Для одновременных операций используются общая транзакционная блокировка управления аккаунтами и блокировки строк; updatedAt увеличивается сервером.

Пароль 12–128 символов назначается при создании/сбросе и передаётся пользователю лично. До личной смены доступны только вход, сведения о своей сессии, смена пароля и выход. Пароль нельзя получить повторно. Отключение, смена роли/логина и сброс пароля завершают все сессии пользователя; изменение собственного доступа требует нового входа. Включение аккаунта не восстанавливает старые сессии. Учётные записи не удаляются физически.

История имеет фильтры по разделу, ID объекта, автору и периоду, пагинацию и сравнение «До/После». GET /api/audit поддерживает entity=users; журнал и изменение записываются одной транзакцией, включая отзыв сессий. В событиях сброса/смены пароля хранятся только признаки действия, без паролей, хэшей и токенов. Время в UI — часовой пояс устройства; имя/логин автора отображаются из текущей учётной записи, ID автора сохраняется.

Если ответ управления аккаунтом не получен, форма сохраняется и показывает неопределённость: проверьте список и историю перед повтором. Автоматического повторного запроса нет. После истечения сессии войдите снова в той же странице, чтобы сохранить черновик. При переключении вкладок незавершённый запрос сохраняет блокировку формы.

## Production на новом сервере

Исходный код: https://github.com/Akezhan7/packera.git. Каталог приложения /srv/packera; данные PostgreSQL, загруженные фотографии и резервные копии — /srv/pakera-data. Дампы, старый PostgreSQL cluster, фотографии пользователей и секреты исключены из Git и Docker-контекста. Прежняя Git-история сохранена локально отдельно; репозиторий имеет новую историю.

Образ собирается на Node 24 из package-lock.json через npm ci. Runtime работает под node (UID 1000). Каталог products на хосте должен быть доступен UID 1000. PostgreSQL 15 используется в отдельном контейнере, порт БД наружу не опубликован. Приложение слушает только 127.0.0.1:3031; его публикует отдельный контейнер packera-tunnel. Токен туннеля находится в /etc/packera/tunnel.token вне репозитория. Изменение исходного туннеля других проектов не требуется.

Создать защищённый файл .env по .env.example (chmod 600). POSTGRES_PASSWORD — случайный длинный hexadecimal пароль; PACKERA_DATA_DIR — /srv/pakera-data; APP_IMAGE — образ текущего релиза. Сам .env в резервный архив не включается; при восстановлении на новом сервере можно назначить новый пароль PostgreSQL. После первого восстановления снимка запустить docker compose up -d --wait; миграции приложения применяются автоматически без очистки существующего содержимого.

Первоначальное восстановление выполняется в пустой новой БД перед запуском app через psql --set ON_ERROR_STOP=1. Для проверки миграции тесты используют локальный packera-database-handover-20261001.sql (его взять из защищённой копии, не публиковать в Git). Пароль первого главного администратора задаётся отдельно через scripts/create-admin.js; боевые аккаунты не копируются из локальной тестовой базы.

TRUST_PROXY=1 включён только в production Compose: внешний трафик должен идти через один доверенный cloudflared, прямой доступ к origin из Интернета закрыт. Express использует правый адрес X-Forwarded-For; без этой настройки forwarding-заголовки не предоставляют клиенту доверенный IP. API каталога и авторизации не кэшировать в Cloudflare; не создавать Cache Everything для /api/* или /admin.

Обновление из выбранного коммита: bash /srv/packera/scripts/deploy.sh COMMIT_SHA. Скрипт проверяет origin и чистоту tracked-файлов, блокирует параллельный деплой, собирает образ packera:COMMIT_SHA, делает резервную копию и ждёт healthcheck. При ошибке останавливается с ненулевым статусом, без скрытого восстановления БД. Образы прежних релизов сохраняются.

Резервная копия: bash /srv/packera/backup.sh. Архив содержит database.sql и products, хранится в /srv/pakera-data/backups с закрытыми правами; retention 14 дней. Копии должны дополнительно переноситься вне сервера. Для первоначальной публикации отдельная копия переносится на локальный компьютер. На новом сервере установлен crontab пользователя serveradmin: каждые 12 часов запускается backup.sh; журнал /srv/pakera-data/backups/backup.log. Проверить расписание: crontab -l.

Откат приложения возможен через APP_IMAGE=packera:PREVIOUS_SHA docker compose up -d app, если прежнее приложение совместимо с применёнными миграциями. Не восстанавливать старую БД поверх новых правок: сначала сохранить актуальный dump, проверить изменения схемы/данных и согласовать восстановление. Старый сервер при первом переносе сохраняется как исходная копия; после переключения домена записи на нём блокируются, чтобы исключить две расходящиеся БД.

При первоначальном переносе 04.10.2026 старое приложение остановлено с restart=no, а старый Nginx временно проксирует запросы на preview.packera.kz через Cloudflare (TLS-проверка включена). Это обеспечивает одну рабочую БД для клиентов со старым DNS. Исходный Nginx и финальный старый dump: /root/vue/backups/packera-final-20261004_112439. Старый PostgreSQL использует пользователя postgres; новый — packera. После CNAME @/www на туннель старый сервер сохраняется только для клиентов с кешированным DNS и исходной копии. Не запускать старое приложение параллельно с новым.

Публикация завершена 04.10.2026: https://packera.kz и https://www.packera.kz работают напрямую через туннель; админка https://packera.kz/admin. Первичный главный аккаунт admin; персональные аккаунты создавать на странице «Пользователи». Случайный пароль первичного аккаунта передан владельцу отдельно и не включён в Git. Полная локальная копия исходных фотографий и мигрированной БД: backups/deployment-20261004/products.tar.gz и database.sql; эти файлы исключены из Git.

Сортировка по задачам хранится отдельно в products.taskSortOrders (позиция по ID задачи). Перетаскивание и стрелки сохраняют порядок только выбранной задачи и её приоритеты; общий sortOrder и categorySortOrder не меняются. Миграция 003-task-order однократно переносит текущий общий порядок в каждую назначенную задачу; ранее утраченную расстановку она не восстанавливает. После обновления все открытые вкладки админки нужно перезагрузить: прежние групповые запросы сортировки отклоняются с CLIENT_UPDATE_REQUIRED. Версии товара продолжают защищать от устаревших записей; при конфликте обновить каталог и повторить своё изменение.
