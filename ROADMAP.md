# Packerra — roadmap надёжного сохранения и личных аккаунтов

> Выполнение: последовательно в этой сессии. После каждого крупного этапа остановка и сообщение пользователю. Для выполнения применяются superpowers:executing-plans, systematic-debugging и test-driven-development. Прямое поручение пользователя разрешает начать после составления roadmap.

**Цель:** подтверждённое сервером сохранение не исчезает при работе других сотрудников; каждый входит под своим аккаунтом, главный администратор управляет доступом, изменения имеют автора и время.

**Архитектура:** сохранить Vue + Express + PostgreSQL. Заменить запись полного снимка на адресные операции с атомарной проверкой версии, транзакциями и журналом изменений. Сервер проверяет сессию и роль на каждом защищённом запросе.

**Стек:** существующие Vue 3, Express 5, pg; node:test для интеграционных проверок; отдельный PostgreSQL 15 в Docker для тестов. Новые зависимости вводить только при доказанной необходимости.

**Спецификация:** согласованные требования и решения ниже; этот файл служит roadmap и записью прогресса.

## Ограничения и критерии продукта

- Работа только в `D:\Work\pakera`. Боевой сервер, его БД и файлы не менять; публикация требует отдельного поручения.
- В checkout уже есть изменения старого разработчика. Сохранять их; не делать reset, массовое форматирование или коммит всей папки. Перед изменением приложения выделить рабочую ветку, сохранив фактический локальный код, а не только старый HEAD.
- Основную локальную БД `pakera-local-db` не использовать для тестов; проверять миграции на изолированной копии. После каждого этапа останавливать запущенное для проверки окружение.
- Витрину, корзину, дизайн и структуру полей товаров сохранять, кроме необходимых состояний сохранения и новых разделов админки.
- Два сотрудника редактируют разные товары: обе записи сохраняются. Один товар: устаревшая запись получает HTTP 409, данные первого сотрудника остаются в БД.
- Удаление только явной операцией по идентификатору и версии; отсутствие товара в снимке браузера не является командой удаления. Удалённый товар не восстанавливается устаревшим запросом.
- Ошибка сети, БД или конфликт не закрывают форму и не уничтожают черновик. Подтверждение «Изменения сохранены» появляется только после успешного ответа сервера после COMMIT.
- Проверка версии атомарна в PostgreSQL: `UPDATE ... WHERE id = ... AND version = ... RETURNING ...`; сначала SELECT, потом безусловный UPDATE не защищают от гонки.
- Массовые операции, сортировка, переименование категории и удаление задачи выполняются транзакционно; конфликт любого затронутого объекта отменяет всю операцию.
- Каждый запрос имеет собственный неизменяемый payload; отложенная очередь не читает повторно изменившийся общий reactive-массив. После конфликта автоматической перезаписи нет.
- Главный администратор управляет аккаунтами; редактор управляет содержимым. Роль проверяется на сервере. Последнего действующего главного администратора нельзя отключить или понизить.
- Имена/логины Анаса, Аины и Лизы вводятся при создании аккаунтов. Не создавать реальные аккаунты с выдуманными паролями.
- Журнал: автор, действие, объект, изменённые поля, время сервера; запись в той же транзакции, что и изменение. Пароли, токены и cookie в журнал не включать.
- Все контрольные тесты должны стать зелёными к финальной приёмке. Красные тесты этапа 1 — ожидаемое подтверждение дефекта, а не исправление.

## Что подтверждено в текущем коде

- `src/data.js:1519`: `saveDatabase()` отправляет products, categories, tasks, banners и siteSettings целиком; очередь существует только внутри одной вкладки.
- `server.js:192`: `/api/save` без проверки версии перезаписывает строки и удаляет объекты, отсутствующие в присланных массивах.
- `src/components/AdminPanel.vue:939`: форма сначала меняет общий массив и закрывается, затем запускает сохранение без await.
- `src/components/AdminPanel.vue:109–149`: вход определяется frontend-проверкой и флагом sessionStorage. Серверные save/upload/reset не проверяют пользователя.

## Риски, которые обязательно проверить

1. Несколько операций над одной сущностью внутри одной вкладки: правильная очередность версий и отсутствие повторной отправки устаревшего draft.
2. Переименование категории/удаление задачи при открытой карточке товара: сервер не восстанавливает старые связи, stale сохранение получает конфликт.
3. Ответ потерян после COMMIT: повторный клик не создаёт дубликат, UI показывает неопределённость и проверяет состояние.
4. Импорт/массовая сортировка со stale версиями: полный rollback вместо частичного перезаписывания.
